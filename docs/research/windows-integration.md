# Windows integration investigation

Research date: 2026-11-12. Status: design findings only; Windows prototype and native acceptance remain open. This document does not select supported Windows versions or establish desktop support.

The environment inspected for this investigation is Ubuntu 26.04.1 LTS, Linux 7.0.0-42-generic, `XDG_SESSION_TYPE=wayland`, `XDG_CURRENT_DESKTOP=ubuntu:GNOME`. No native Windows desktop or Explorer session is available. No Windows implementation, package, installation, timing measurement, or smoke test was performed. The parent task's Git baseline prerequisite remains blocked by read-only `.git`; this investigation writes only this findings file.

## Documentation method

Used the installed Context7 skill, resolved “Windows Win32 Shell APIs” to `/websites/learn_microsoft_en-us_windows_win32_api`, and separately queried foreground selection, hotkey registration, and context-menu invocation. Context7 supplied the Win32 API contracts but did not answer current package registration or Windows 11 tab mapping sufficiently. Official Microsoft documentation and Microsoft's Explorer automation example fill those gaps where possible. Native tab behavior remains an evidence gap.

## Smallest proposed vertical slice

After the design baseline is committed, build a disposable Windows adapter prototype with three small responsibilities: a per-user helper owns shortcut registration and the conversion popup; a selection adapter snapshots the invoking Explorer view; a minimal context-command COM component forwards a selected-item snapshot to the helper. Keep all Windows objects outside the Rust core. No converter implementation belongs in this slice.

The prototype should display an explicitly labeled integration-test action and selected-file count, then return the chosen action or cancellation. It must not advertise a working conversion route. Both entry points must open this transient conversion popup directly after installation/setup, with no manual application launch. Proposed seams are `ShortcutAdapter`, `SelectionAdapter`, `PopupPresenter`, and a bounded activation request carrying a frozen selection. Exact wire format and startup registration remain implementation decisions requiring documentation and tests.

### Shortcut and foreground selection

Use `RegisterHotKey` with a configurable binding and `MOD_NOREPEAT`; process `WM_HOTKEY` on the owning thread's message loop. A zero registration result requires `GetLastError` and visible conflict/setup feedback. Reserved Windows-key combinations and F12 are unsuitable defaults. On settings changes, attempt the replacement binding with a distinct identifier before retiring the working registration; persist only successful settings. Remove registrations on quit. Microsoft's contract describes registration failure for an already registered binding and explicit removal through `UnregisterHotKey`. [RegisterHotKey](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerhotkey), [UnregisterHotKey](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-unregisterhotkey).

Capture `GetForegroundWindow()` immediately when handling the invocation, before showing any FileShift UI; a null handle is a recoverable unsupported-context result. It identifies the user's foreground window, whereas thread-local active-window queries are insufficient. [GetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getforegroundwindow).

The concrete Explorer mapping candidate follows Microsoft's example: enumerate `IShellWindows`; query each dispatch for `IWebBrowserApp`; compare its `get_HWND` with the captured handle; then obtain `IServiceProvider`, query `SID_STopLevelBrowser` for `IShellBrowser`, and call `QueryActiveShellView`. Do not take the first Explorer instance or match only the folder path. That historical example establishes a composable API route, not current tab correctness. [Querying information from an Explorer window](https://devblogs.microsoft.com/oldnewthing/20040720-00/?p=38393).

For a matched automation view, `Document.SelectedItems()` returns all selected items; copy their paths immediately. A native alternative is to query the active shell view for `IFolderView2` and call `GetSelection(FALSE)`, which returns an `IShellItemArray` without substituting the parent folder when nothing is selected. Prefer the native route for shared validation with context-command selections; compare both during the disposable prototype if tab behavior is ambiguous. [ShellFolderView.SelectedItems](https://learn.microsoft.com/en-us/windows/win32/shell/shellfolderview-selecteditems), [IFolderView2::GetSelection](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ifolderview2-getselection).

Recheck foreground identity before presenting the result; abort capture if the user switches context during collection. This is a proposed race policy, not an atomic Shell guarantee. Never reread the live selection after the popup opens. Windows 11 multi-tab Explorer must be tested with different selections in each tab: matching a top-level HWND alone cannot serve as evidence that the active tab was captured. Ambiguous matches fail with actionable status until resolved. Non-Explorer focus, no selection, and COM errors report “Select files in Explorer and try again” or a specific setup diagnostic; no clipboard reading, folder scans, or background-window fallback.

### Right-click activation and packaging

Use `IExplorerCommand::Invoke`'s `IShellItemArray` directly as the invocation selection. Snapshot it before returning; never reacquire foreground selection for this entry point. Keep menu construction fast, then pass work to the helper. [IExplorerCommand::Invoke](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-iexplorercommand-invoke), [IExplorerCommand](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nn-shobjidl_core-iexplorercommand).

The current Microsoft route for Windows 11's modern menu is a native COM command DLL, package identity, a `windows.comServer` registration, and `windows.fileExplorerContextMenus` association with the same CLSID. A full package or sparse package for externally installed binaries is possible. Register files (`*`), excluding folder/background contexts for this product. DLL architecture must match Explorer. Installation must manage registration and removal. [Packaged desktop app integration](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/integrate-packaged-app-with-file-explorer).

Prefer a signed full package for the prototype if startup integration permits; otherwise evaluate a signed sparse identity package managed by the native installer. This is a candidate, not a settled distribution decision. A classic registry verb or `IContextMenu` proof may help isolate invocation issues, but on Windows 11 the legacy surface is under “Show more options”; it does not prove modern-menu integration. Microsoft identifies `IExplorerCommand` and runtime package identity as modern-menu requirements. [Windows app best practices](https://github.com/MicrosoftDocs/windows-dev-docs/blob/docs/hub/apps/get-started/best-practices.md). Actual visibility, trust/signing, multi-selection delivery, and installed activation on the chosen Windows build remain unverified. Do not replace the required direct right-click-to-popup flow with Open with, Send to, or manual launch.

### Popup, input safety, and permissions

A small native menu avoids choosing a cross-platform GUI toolkit prematurely. Create the conversion popup with an owner window and `TrackPopupMenuEx`, near the invocation pointer, using `TPM_RETURNCMD`; cancellation produces no work. Verify arrows, Enter, Escape, outside-click dismissal, monitor scaling, and repeated activation. Windows documents menu positioning and recommends `TrackPopupMenuEx` for new applications. Foreground activation is restricted and can fail; keyboard focus must be demonstrated for both entry points rather than assumed from `SetForegroundWindow`. [Using menus](https://learn.microsoft.com/en-us/windows/win32/menurc/using-menus), [TrackPopupMenu](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-trackpopupmenu), [SetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow).

Normalize both entry points to the same validation boundary. Virtual items are not ordinary filesystem inputs; `FolderItem.IsFileSystem` and native filesystem names are useful first checks, not sufficient security validation. Reject directories, reparse/symlink inputs under v1 policy, unreadable or stale files, remote URLs, UNC paths and mapped network drives; report reasons per item. `GetDriveTypeW` distinguishes remote drives. Recheck file identity when eventually opening it. [IsFileSystem](https://learn.microsoft.com/en-us/windows/win32/shell/folderitem-isfilesystem), [GetDisplayName](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ishellitem-getdisplayname), [GetDriveTypeW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getdrivetypew).

Proposed privilege model: ordinary user session, no elevation for everyday use, no injected input hooks or UI scraping, and no generic disk-access grant. Access denial must remain explicit. IPC must authenticate the same user, bound payload sizes, and treat every received path as untrusted. Do not log paths by default.

Prefer structured local IPC over embedding paths in a command string. Any process launch uses an allowlisted absolute executable and argument-vector construction, never `cmd.exe`, PowerShell, batch files, or shell expansion. Windows ultimately accepts a command line: native launching must set `lpApplicationName` explicitly and apply quoting matching the receiving executable's parser. Test Unicode, spaces, metacharacters and large selections. Microsoft's `CreateProcessW` documentation explains executable ambiguity when the application name is omitted. [CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw).

## Native acceptance evidence required

- Record exact Windows edition/build, Explorer executable version, architecture, package type/version/signing, user privilege and session; record clean install, startup after sign-in, upgrade, quit, and uninstall outcomes.
- Invoke both entry points with one file and a mixed multi-selection; compare actual selected paths privately with the snapshot. Change the selection afterward and verify it stays frozen.
- Open two Explorer windows and multiple tabs with different selections; verify only the foreground active view is captured. Test tab switching, navigation, focus changes during capture, Home/search views and unsupported virtual locations.
- Verify empty selection, unsupported app, inaccessible/deleted files, directories, network locations and reparse points produce clear status without fallback reads.
- Occupy the chosen hotkey with another process; verify conflict feedback, recovery, rebinding and release on quit.
- Verify modern-menu visibility on the chosen Windows 11 build, keyboard invocation, multi-selection, cold helper activation and no main window. Record classic-menu observations separately.
- Verify popup focus, keyboard navigation, Escape, outside click, repeated invocation and display scaling. Measure idle CPU/RSS and cold/warm activation latency before proposing numerical budgets.
- Verify path transport never executes metacharacters, bounded requests fail safely, and uninstall removes startup, command and shortcut registrations.

Completion blockers: design baseline not committed; no native Windows environment; no implementation or signed package; active-tab mapping, startup configuration, foreground popup behavior and installed lifecycle unproven. Keep the Windows prototype and feasibility gate open. Core mocks and cross-compilation cannot close them.
